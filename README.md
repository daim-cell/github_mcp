# GitHub MCP and ACP Research Agents

A Python project that combines a GitHub MCP server with local agent workflows for repository research.

The project wraps the GitHub API with practical operations for repository discovery, repository file inspection, issue management, and pull request review. It also includes a LangGraph/Ollama CLI agent and a multi-agent ACP pipeline with planner, researcher, and writer agents coordinated by a supervisor graph.

## Repository Components

```text
.
```

## MCP Server

`server.py` creates a `FastMCP("github-mcp")` server and registers six GitHub tools. It validates the configured GitHub token before accepting stdio MCP connections.

## Tools

The FastMCP server registers six MCP tools.

### `search_repositories`

Search GitHub repositories and return concise metadata.

Arguments:

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `query` | `str` | Required | GitHub repository search query |
| `max_results` | `int` | `5` | Maximum repositories to return |

Returns repository name, description, URL, stars, forks, language, open issue count, and topics.

### `list_directory`

List files and directories in a GitHub repository path.

Arguments:

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `repo` | `str` | Required | Repository in `owner/name` format |
| `path` | `str` | `""` | Directory path inside the repository |
| `branch` | `str` | `"main"` | Branch or ref to read from |

Returns each item name, path, type, size, and GitHub URL.

### `get_file_contents`

Fetch the contents of a single file from a GitHub repository.

Arguments:

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `repo` | `str` | Required | Repository in `owner/name` format |
| `path` | `str` | Required | File path inside the repository |
| `branch` | `str` | `"main"` | Branch or ref to read from |

Returns file metadata plus decoded UTF-8 content. If the path is a directory, use `list_directory` instead.

### `list_issues`

List repository issues, optionally filtered by state and label.

Arguments:

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `repo` | `str` | Required | Repository in `owner/name` format |
| `state` | `Optional[str]` | `None` | Issue state. Defaults to `open` when omitted |
| `label` | `Optional[str]` | `None` | Optional label name |
| `max_results` | `int` | `10` | Maximum issues to return |

Pull requests are filtered out of the issue results.

### `create_issue`

Create a new GitHub issue.

Arguments:

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `repo` | `str` | Required | Repository in `owner/name` format |
| `title` | `str` | Required | Issue title |
| `body` | `str` | `""` | Issue body |
| `labels` | `list` | `None` | Optional label names |

Use this tool only with repositories where your token has write access. Unknown labels are skipped.

### `get_pull_requests`

List repository pull requests, optionally filtered by state and base branch.

Arguments:

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `repo` | `str` | Required | Repository in `owner/name` format |
| `state` | `str` | `"open"` | Pull request state, such as `open`, `closed`, or `all` |
| `base` | `str` | `""` | Optional base branch filter |
| `max_results` | `int` | `10` | Maximum pull requests to return |

Returns PR number, title, state, author, base/head branches, mergeability, creation time, HTML URL, and diff URL.

## Setup

### 1. Create a virtual environment

```bash
python -m venv .venv
source .venv/bin/activate
```

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Configure environment variables

Copy the example file and add your token:

```bash
cp .env.example .env
```

Required:

```env
GITHUB_TOKEN=ghp_your_token_here
```

`utils/auth.py` also accepts `GITHUB_KEY` as a fallback name. The token is validated when `server.py` starts.

Optional:

```env
OPENAI_API_KEY=sk-your_key_here
COST_PER_1K_INPUT=0.00
COST_PER_1K_OUTPUT=0.00
BASE_MODEL=qwen2.5:7b
CLASSIFIER_MODEL=llama3.2:3b
TAVILY_API_KEY=tvly-your_key_here
```

The local agents use Ollama. `BASE_MODEL` controls the main GitHub research and synthesis models, while `CLASSIFIER_MODEL` controls input and output validation. `TAVILY_API_KEY` is used by the ACP researcher when a research brief requires public web search. Cost variables are used for tracing metadata when token usage is reported by the model provider.

## Running the MCP Server

Start the server directly:

```bash
python server.py
```

The server uses stdio transport. MCP JSON-RPC messages flow through stdin/stdout, while server and tool logs are written to stderr.

On startup, the server validates GitHub authentication and prints the authenticated username to stderr. If authentication fails, it exits before accepting connections.

## MCP Client Configuration

Use the Python entrypoint from this repository in your MCP client configuration.

Example:

```json
{
  "mcpServers": {
    "github-mcp": {
      "command": "python",
      "args": ["/absolute/path/to/github_mcp/server.py"],
      "env": {
        "GITHUB_TOKEN": "YOUR_GITHUB_TOKEN"
      }
    }
  }
}
```

Adjust the command path if your MCP client needs the virtual environment Python executable, for example:

```json
"command": "/absolute/path/to/github_mcp/.venv/bin/python"
```

## Local Agent

`agent.py` starts `server.py` as a stdio MCP subprocess, converts the MCP tools into LangChain structured tools, and runs a ReAct-style LangGraph agent in an interactive shell.

The agent now includes:

* input validation for prompt-injection patterns, out-of-scope queries, and maximum query length
* an LLM-based query classifier for GitHub relevance and injection detection
* a planning step that prints a numbered execution plan before tool use
* per-tool call limiting to prevent repeated loops
* response validation with a retry path for incomplete or unsafe answers
* issue-list response checks that expect issue numbers for issue queries
* Phoenix/OpenTelemetry tracing for queries, plans, tools, latency, tokens, and estimated cost
* configurable base and classifier Ollama models

The default models are:

```python
BASE_MODEL = "qwen2.5:7b"
CLASSIFIER_MODEL = "llama3.2:3b"
```

Before running the agent, make sure Ollama is installed and the models are available locally:

```bash
ollama pull qwen2.5:7b
ollama pull llama3.2:3b
python agent.py
```

`agent.py` launches a local Phoenix app when it starts and registers traces under the `github-mcp-agent` project. If your environment does not already include Phoenix, install the package that provides the `phoenix` module before running the agent:

```bash
pip install arize-phoenix
```

Then ask GitHub-related questions at the prompt:

```text
> Search for popular Python MCP servers
> List open issues in owner/repo
> Show the README from owner/repo on main
```

The agent includes a small fallback that converts plain JSON tool-call text into structured LangGraph tool calls. This helps local models that sometimes emit tool calls as text instead of native function calls.

## ACP Agents

The repository now includes an Agent Communication Protocol pipeline built with `acp-sdk`. Each ACP agent runs as a small local HTTP service and exposes one named agent.

| Service | Command | URL | Agent | Role |
| --- | --- | --- | --- | --- |
| Planner | `python -m agents.planner` | `http://127.0.0.1:8001` | `planner` | Turns a topic into an approved research brief |
| Researcher | `python -m agents.researcher` | `http://127.0.0.1:8002` | `researcher` | Answers brief questions using GitHub MCP tools and optional Tavily web search |
| Writer | `python -m agents.writer` | `http://127.0.0.1:8003` | `writer` | Retrieves stored findings and synthesizes the final document |

### Planner Agent

`agents/planner.py` accepts a topic and generates a structured brief:

```python
class PlannerOutput(BaseModel):
    topic: str
    key_questions: list[str]
    required_sources: list[str]
    output_format: str
    approved: bool
```

The planner yields the draft brief and waits for human approval through ACP resume support. Reply with `approve` to continue or `revise: <feedback>` to request another draft. The planner allows up to three revision attempts before auto-approving the last valid brief.

### Researcher Agent

`agents/researcher.py` accepts the approved `PlannerOutput` JSON. For each key question, it:

* validates the question using the same input guardrails as the CLI agent
* opens a GitHub MCP session through `utils/mcp_session.py` when GitHub sources are required
* adds a Tavily `web_search` tool when the brief includes `web`
* runs a LangGraph ReAct agent with a step cap and per-question timeout
* stores successful findings in shared ChromaDB memory

The researcher returns:

```python
class ResearcherOutput(BaseModel):
    topic: str
    questions_answered: list[str]
    questions_unanswered: list[str]
    findings_stored: int
```

Each question is limited to 8 tool steps and 120 seconds.

### Writer Agent

`agents/writer.py` accepts the approved brief plus the researcher summary. It retrieves relevant findings from shared memory, deduplicates them, and synthesizes a structured document using only retrieved context.

The writer returns:

```python
class WriterOutput(BaseModel):
    document: str
    sources_used: list[str]
    validation_passed: bool
```

The final document is checked with the safety classifier before being returned.

## ACP Supervisor

`supervisor.py` coordinates the ACP agents with a LangGraph `StateGraph`:

```text
validate_input
  -> run_planner
  -> run_researcher
  -> run_writer
  -> human_checkpoint
```

If validation fails or an agent returns invalid output, the graph routes to `error`. If the researcher answers fewer than three questions, the supervisor retries the researcher once with an additional retry note. At the end, the supervisor prints the final document and asks for `publish` or `discard`.

Run the ACP services in separate terminals:

```bash
chroma run --path .chromadb --port 8010
python -m agents.planner
python -m agents.researcher
python -m agents.writer
```

The ChromaDB server must stay running while the ACP pipeline is active. The researcher and writer are separate processes, so they share memory through Chroma's HTTP server at `127.0.0.1:8010`.

Then start the supervisor:

```bash
python supervisor.py
```

You can also pass the first topic as command-line text:

```bash
python supervisor.py "Compare the GitHub activity of popular Python MCP servers"
```

Pipeline runs are logged to:

```text
logs/pipeline_runs.jsonl
```

## Shared Memory

`memory/shared_store.py` provides the researcher and writer with shared persistent memory backed by ChromaDB.

For the ACP pipeline, run ChromaDB as a separate local server before starting the agents:

```bash
chroma run --path .chromadb --port 8010
```

The shared store connects to:

```text
127.0.0.1:8010
```

This is needed because the ACP planner, researcher, writer, and supervisor run in separate processes. The Chroma HTTP server owns the local index and prevents unsafe concurrent access to `.chromadb`.

Findings are split into overlapping token chunks:

* chunk size: 512 tokens
* overlap: 50 tokens
* server host: `127.0.0.1`
* server port: `8010`
* storage path: `.chromadb`
* collection name: `research_findings`

The researcher writes chunks with topic and question metadata. The writer retrieves by broad topic and by each planned question, then deduplicates chunks before synthesis.

## ACP Smoke Test

`test_ping.py` runs a direct end-to-end smoke test against the three ACP services. Start the planner, researcher, and writer services first, then run:


## Agent Validation Flow

Each interactive query follows this flow:

```text
user query
  -> length and prompt-injection regex checks
  -> LLM classifier for GitHub scope and injection risk
  -> planner LLM produces an execution plan
  -> LangGraph ReAct agent calls MCP tools
  -> output validation and optional one-time retry
  -> final answer
```

Validation settings live in `constants.py`:

| Constant | Purpose |
| --- | --- |
| `MAX_QUERY_LENGTH` | Rejects overly long queries. Current limit: `2000` characters |
| `INJECTION_PATTERNS` | Regex patterns for common prompt-injection attempts |
| `ISSUE_QUERY_PATTERNS` | Detects issue-list style prompts |
| `ISSUE_RESPONSE_PATTERN` | Checks that issue responses include issue numbers |
| `OUTPUT_FALLBACK` | Fallback text when response validation cannot produce a valid answer |
| `BRIEF_SYSTEM_PROMPT` | Prompt used by the ACP planner to produce research briefs |
| `WRITER_SYSTEM_PROMPT` | Prompt used by the ACP writer to synthesize final documents |
| `*_SYSTEM_PROMPT` | Prompts for classification, planning, safety review, and agent behavior |

## Logging and Rate Limits

Every tool is wrapped with `utils.logger.log_tool_call`.

Logs are written to:

```text
logs/tool_calls.jsonl
```

Each JSONL record includes:

* timestamp
* tool name
* inputs
* summarized output
* latency in milliseconds
* success/error status
* remaining GitHub core API rate limit

Before each GitHub call, `guard_rate_limit()` checks the core API quota. If fewer than 10 requests remain, the tool raises a clear rate-limit error with the reset time.

The agent also records OpenTelemetry spans for:

* `input.validation`
* `plan`
* each MCP tool call
* `output.validation`
* the full `agent.query`

Tool spans include input/output token estimates, latency, success status, and output summaries. LLM spans receive token and cost attributes when usage data is available.

ACP pipeline run summaries and shared-memory writes are recorded in `logs/pipeline_runs.jsonl`.

## Notes

* Repository arguments use GitHub's `owner/name` format.
* File and directory tools default to the `main` branch. Pass `branch` explicitly for repositories that use another default branch.
* `create_issue` requires a token with write permissions for the target repository.
* The ACP researcher requires `TAVILY_API_KEY` only when a brief includes `web` in `required_sources`.
* Start `chroma run --path .chromadb --port 8010` before running the ACP researcher and writer.
* `.chromadb` is created locally when the ChromaDB server stores findings.
* Tool outputs are intentionally compact so downstream agents can reason over them without receiving unnecessary GitHub API detail.
